# Общие вложения в существующем приложении

[← README](../../README.md) · [English](application.en.md) · [Справочник API](reference.ru.md) · [Версии](../index.md)

Вложение часто видно дважды: в сообщении и в панели просмотра. Кэш позволяет обоим представлениям использовать одно загруженное медиа, не связывая их время жизни. Начните с HTTP-загрузчика и именованного профиля; своё хранилище или загрузчик добавляйте, когда этого требует приложение.

## Подключение медиа-эндпоинта

В приложении уже есть сессия и авторизованный endpoint медиа. Добавьте `@59alex/browser-media-cache: 0.1.0` в dependencies package.json. Публикация пока не выполнена; для оценки используйте [локальный пакет](ru.md#подготовка).

```ts
import { createHttpMediaCache } from '@59alex/browser-media-cache';
const media = createHttpMediaCache({
  url: ({ namespace, key }) => `/api/accounts/${encodeURIComponent(namespace)}/media/${encodeURIComponent(key)}`,
  request: () => ({ credentials: 'same-origin' }),
});
```

Сервер проверяет, разрешено ли вошедшему пользователю читать аккаунт и файл. Аккаунт в пути — не авторизация. `request` может асинхронно получать актуальные credentials с переданным `signal`; callback запускается только при необходимости сетевой загрузки. Свой авторизованный fetch передайте через `fetch`. Фабрика устанавливает GET, свой сигнал отмены, `cache: 'no-store'` и `redirect: 'error'`: указывайте конечный адрес вместо перенаправления.

Фабрика проверяет HTTP-статус до чтения тела, отклоняет слишком большой объявленный Content-Length, затем считает фактические байты ответа. Отсутствующая или неточная длина не отключает ограничение. Дедлайн 30 секунд охватывает настройку запроса, заголовки и тело; по его истечении операция отменяется. Только успешно загруженный Blob становится общим ресурсом. Сетевые/декодирующие буферы и сборка Blob временно могут использовать дополнительную память: лимит ответа не является гарантией общего размера heap.

## Разбор полного примера вложений

[http-attachments.ts](../../examples/http-attachments.ts) можно перенести в модуль медиа браузерного приложения. Функции следуют времени жизни представления:

1. `createAttachmentCache` вызывается один раз при запуске приложения в браузере. Он выбирает `previews` и endpoint с авторизацией сессии; все компоненты получают этот экземпляр.
2. `showAttachment` получает handle для namespace/key и устанавливает URL после готовности. Abort-listener удаляет DOM-ссылку, если инвалидация прекратила владение.
3. Возвращаемый cleanup сначала удаляет `src`, затем освобождает handle. Зарегистрируйте cleanup во фреймворке или вызовите при удалении представления.
4. `forgetAccount` вызывается после удаления представлений аккаунта и ожидает инвалидацию, включая очистку необязательного постоянного хранилища.
5. `cache.dispose()` вызывает только владелец приложения при окончательном завершении работы. Общий виджет не должен уничтожать чужой экземпляр.

Границы времени жизни отмечены соседними комментариями EN/RU. В React готовые [MediaGallery и MediaPreview](https://github.com/dlorian59/browser-media-cache-react/blob/main/docs/0.1.0/application.ru.md) уже реализуют отображение и освобождение ресурсов.

## Выбор профиля

| Профиль | Для чего | Максимум HTTP-медиа | Удержание без владельцев | Записи / байты кэша |
|---|---|---|---|---|
| `previews` (по умолчанию) | Изображения и короткие аудио/видеовложения | 8 MiB | 30 с | 128 / 64 MiB |
| `avatars` | Много небольших аватаров | 2 MiB | 60 с | 256 / 16 MiB |
| `transient` | Немедленное освобождение неиспользуемых медиа | 8 MiB | 0 | 0 / 0 |

```ts
const media = createHttpMediaCache({ profile: 'avatars', url: ({ key }) => `/avatars/${encodeURIComponent(key)}` });
```

У всех профилей дедлайн по умолчанию 30 секунд. Переопределяйте `maxMediaBytes` или `timeoutMs`, если требования endpoint известны. Прежние `idleTtlMs`, `maxEntries`, `maxBytes` также можно задать. `MEDIA_CACHE_PROFILES` содержит замороженные числовые настройки для своего `new MediaCache({ load, ...profile })`; пользовательский load сам отвечает за предел загрузки и дедлайн.

Жёсткий предел HTTP и мягкий бюджет кэша решают разные задачи. `maxMediaBytes` отклоняет отдельную слишком большую загрузку. При превышении `maxBytes` или числа записей кэш вытесняет только неиспользуемые ресурсы; активные владельцы сохраняют ресурс и могут превышать целевые значения. Декодирование, текущие сетевые буферы и постоянное хранилище не входят в счётчик удерживаемых байтов.

## Два представления, одна загрузка

```ts
const first = media.acquire({ namespace: accountId, key: 'photo:42:v3' });
const second = media.acquire({ namespace: accountId, key: 'photo:42:v3' });
const [a, b] = await Promise.all([first.ready, second.ready]);
// EN: a.url === b.url; removing one view preserves the other owner's resource.
// RU: a.url === b.url; удаление одного представления сохраняет ресурс второго владельца.
first.release();
// Позже, при закрытии второго представления:
second.release();
```

Идентичность ресурса — namespace и key в одном экземпляре кэша. Разные экземпляры не разделяют владение. При изменении файла используйте новую версию ключа: `photo:42:v4` получает новый ресурс, не отзывая неожиданно URL `v3` у другого представления.

Для отмены одного ожидающего представления передайте его `AbortSignal` в `acquire` либо освободите handle. Общая загрузка продолжается, пока нужна другому владельцу; отмена последнего ожидающего владельца прерывает её. HTTP callback должен учитывать сигнал. Callback, игнорирующий отмену, может продолжать свою работу, но фабрика не отправит поздний fetch после его завершения.

## Аккаунты и авторизация

Удалите представления прошлого аккаунта до `invalidateNamespace(oldAccountId)`. Смена namespace изолирует следующие чтения, но не стирает старые данные. При required-хранилище дождитесь инвалидации и обработайте ошибку, прежде чем считать очистку при выходе завершённой.

```ts
await media.invalidateNamespace(oldAccountId);
```

После обновления сессии стабильный callback `request` должен читать текущий токен, а не захваченный при создании кэша. Кэшированные медиа могут выдаваться без новой сетевой проверки прав; инвалидируйте их при прекращении доступа. Namespace — метка, а не credentials; кэш не синхронизирует отзыв сессии между вкладками.

## Если загрузка не удалась

| Ситуация | Результат и действие |
|---|---|
| HTTP 401/403/404/503 | `MediaHttpError` содержит `status`; исправьте авторизацию/доступ или предложите явный повтор. Фабрика сама не обновляет credentials и не повторяет запрос. |
| Слишком много байтов / неверный Content-Length | `RangeError`; выберите конечный файл нужного размера или осознанно измените предел ответа. |
| Истёк дедлайн | `DOMException` с именем `TimeoutError`; запрос/тело отменяются. Повтор определяет политика приложения. |
| Потребитель освобождён или инвалидирован | Владение прекращается, его сигнал отменяется. Уберите URL из UI до release. |
| Браузер не декодирует успешно загруженный Blob | Это ошибка изображения/плеера, а не HTTP-кэша. Проверьте формат/кодек; исправленное содержимое требует нового ключа или осознанной инвалидации. |

Неудачная запись удаляется из кэша; следующий acquire может загрузить её заново. HTTP-фабрика не заменяет ошибки пустыми или фиктивно успешными медиа.

## Хранилище и собственные источники

Фабрика принимает прежние `store`, `persistence`, `onStoreError`, platform hooks и диагностику. При попадании в постоянное хранилище HTTP loader не вызывается: размер и дедлайн HTTP проверяются у сетевых загрузок, а не у сохранённых Blob. Политику хранения выбирайте отдельно. [CacheStorage и квоты](ru.md#необязательный-cachestorage), [свой store](../../examples/custom-store.ts), [свой loader и владение](../../examples/attachments.ts), [platform hooks](../../examples/platform-hooks.ts).
